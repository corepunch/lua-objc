## 2. SwiftUI plan findings

1. **The 158 macOS passes do not verify ordinary production defaults.**
   [The candidate adapter](../../lua/parity/batch.lua) disables stack growth,
   shrinking and fill, subtracts four points from unconstrained text widths,
   and represents padding with an extra wrapper. `runEnvironment()` always
   enables this path. Some modifier translation is necessary, but these
   differences need an explicit public mapping and production/XML tests.
   The adapter's own comments say it preserves different production sizing.
   Resolve the intended public contract before treating these as core passes.
2. **Layout is still failing inside the adapter.** Of the macOS cases,
   HStack has 66 pass / 30 fail, VStack 69 / 27, and ZStack 23 / 9.
   In `hstack.w120.s0.p0.mixed`, SwiftUI wraps “Longer label” to 67×48 points;
   the candidate measures 108×24 and exceeds the available width. Nested
   spacer cases also differ in height and placement. Fix proposal handling,
   wrapping and flexible descendants before tuning full-screen offsets.
3. **The batch is a small subset of the contract.**
   [Its grammar](../../scripts/parity/batch.py) supports only text, HStack,
   VStack, ZStack and Spacer. It does not measure controls, images, grids,
   navigation, lists, sheets, input actions, XML rendering, accessibility,
   dark appearance or text-size/RTL variants. Candidate batch PNG capture is
   explicitly unimplemented. 224 is a parameter matrix, not 224 UI families.
4. **Inventory and coverage accounting remain incomplete.**
   [coverage.md](coverage.md) is a historical family snapshot, not the
   required property/style/platform inventory with fixture links. It still
   describes three seed cases and omits newer XML tags in places. The
   manifest has one status per case rather than independent Lua, XML,
   geometry, appearance, behavior and accessibility statuses. Its validator
   checks the shape of a small set of fields; it does not enforce the full
   acceptance contract or require evidence for a passing claim.
5. **Gate B has missing surfaces, not just unverified ones.** No public
   implementations were found for LazyV/HStack, LazyV/HGrid or ViewThatFits
   in either exported Lua layer. Grid currently composes eager stacks and
   assigns column widths; that is not evidence for SwiftUI grid sizing,
   spanning or lazy realization. Other required semantics such as ordered
   modifiers, fixedSize and layoutPriority still need explicit mappings.
6. **The gallery reporter is not a complete acceptance gate.**
   [report_case.py](../../scripts/parity/report_case.py) compares native
   parent-local frames directly with reference frames, unlike the batch's
   common-root coordinate contract. Its overall `pass` depends on geometry;
   missing/different images and unverified input do not prevent it. It records
   reference action counts without asserting matching candidate actions.
   The current reports are all failing, but a future green report would still
   need these independent gates. Fix this before approving visual baselines.

The September 8 “0/224 on both platforms” handoff remains historical evidence.
Today's adapter-enabled macOS result supersedes that number, not the plan's
requirements. Neither core parity nor common SwiftUI coverage is nearly closed
on the evidence available.

### Data and runtime differences

All nine IDs and all nine copied cover images match (SHA-256 byte comparison).
That is the strongest completed part of the content port. However:

- All nine full descriptions differ; four short descriptions differ.
- All 21 individual review records are absent from the Lua model.
- Review counts differ: Spellbreaker **891 → 942**, Zork II **1872 → 1180**,
  Zork III **1567 → 934**, Limehouse **342 → 214** (Swift → Lua).
- Limehouse's genre changes from **Victorian Mystery** to **Mystery Adventure**.
- The Swift sorted featured set is Planetfall, Sanitarium, Spellbreaker.
  Lua's featured set is Wondertown, Planetfall, Sanitarium, and only Planetfall
  is displayed as a hero.
- Swift pins zilscript `e80d5321`; lua-objc pins `e5a00ef8`. Game/runtime
  behavior cannot be assumed identical across these revisions.
- The Swift backend loads companion files, manages a per-backend Lua state,
  and exposes progress/exits/suggestions/replay. Lua `ZIL.lua` loads a game
  environment but mutates shared `package.path`, `package.zilpath`, and on
  UIKit replaces global `io.open` with a read-only adapter. That needs an
  isolation and storage design before adding concurrent sessions or saves.
- `session:start()` is outside `showSession()`'s `pcall`; startup failures
  do not take the intended error-view path. The current ZIL regression only
  verifies Wondertown loads and produces opening text; it does not prove all
  nine games, replay or companion behavior.

## 4. Architecture and completion order

The thin class-returning `init.lua` is correct. Most other screens are built
inside `Controller.lua`, and `install()` creates/replaces a window from screen
actions. The requested architecture needs further work:

1. Establish one app root/window, model-owned selected tab/routes, and native
   navigation that retains tab and session state. Fix initial Adventures
   selection and flexible tab content first, with actual headless assertions.
2. Port the exact catalog/reviews and pin the intended game/runtime content.
   Keep app state in `Model.lua` with focused catalog, session, storage and
   preferences modules. Keep platform file access scoped to the backend.
3. Implement save/new/continue/replay/delete and typed commands before claiming
   a playable port. Transfer source behavioral contracts into fast Lua tests.
4. Move each screen and reusable card/rating/composer into `views/` components
   returning view trees; use cross-platform etlua with injected `ns` and
   ForEach for repeated siblings. Controller wires actions and model state;
   only its app entry creates the window. Use retained descriptions for
   structural changes.
5. Complete carousel, details/reviews/help, Ongoing, Create, Settings, reading,
   translation and companion UI. Track missing native framework support
   separately from missing app code. Use SF Symbols for ratings, not `★★★★★`.
6. Verify the same deterministic catalog/save/transcript states against the
   Swift app on the same iOS device/runtime. Record platform-appropriate macOS
   behavior separately; this Swift app is UIKit-oriented. Exercise empty,
   loading, error, saved, disabled and long-text states, keyboard/back/focus,
   resizing, light/dark and accessibility before calling it 1:1.

Do not retain temporary placeholder tabs, old navigation paths or compatibility
shims once their replacements exist. The current three app test files have
14 assertions total; five are source-string navigation checks. They must grow
into behavior/state/layout coverage, and the tests that enforce cover-only
navigation must change with the implementation.
